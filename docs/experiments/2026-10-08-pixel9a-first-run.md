# 実験記録：Pixel 9a での初回動作確認

日時: 2026-10-08 11:56〜（JST）
目的: Phase 1 のアプリが実機でスキャン・集計・記録・Ambient 送信まで動くことを確かめる

## 条件

| 項目 | 内容 |
|---|---|
| 端末 | Pixel 9a（Android 16）。USB 給電、モバイル回線（LTE）、Wi-Fi 未接続 |
| アプリ | 0.1.0 debug。`android/scripts/setup-device.sh` で導入（実行時権限は adb で付与、バッテリー最適化から除外） |
| 設定 | 画面常時点灯 ON（最低輝度）、デバッグログ ON、Ambient 送信 ON（チャネル 103428） |
| 場所・在室人数 | 記録していない（実人数との突き合わせは Phase 4 の校正実験で行う） |

## 確認できたこと

| 項目 | 結果 | 根拠 |
|---|---|---|
| Foreground Service（connectedDevice）で常駐 | OK | `dumpsys activity services` で isForeground=true、types=0x10 |
| CPU を止めない | OK | `dumpsys power` に PARTIAL_WAKE_LOCK 'CrowdLevelNode:scan' |
| 常駐画面の常時点灯と最低輝度 | OK | DisplayPowerController が輝度 0.01 の上書きを記録 |
| 分境界での窓の確定 | OK | 各分の :00.02 前後に確定 |
| Ambient への送信 | OK | 確定から約0.5秒で HTTP 200。`created` は窓の開始時刻 |
| 部分的な窓を送らない | OK | 再インストール直後の 12:00 の窓は partial として記録され、送信されなかった |
| 通信断からの再送 | OK | モバイルデータを約40秒切断。12:02 の窓は送信失敗後キューに残り、12:04:00 に再送。続く 12:03 の窓は 5.8 秒後に送信 |
| 端末内ログ（JSON Lines） | OK | `Android/data/com.crowdlevel.node/files/logs/2026-10-08.jsonl` に1分1行。ハッシュは16文字 |

## 観測値（満1分の窓）

| 項目 | 範囲 |
|---|---|
| 受信パケット | 約 46〜55 / 秒（2,817〜3,757 / 分） |
| ユニーク端末数（all） | 109〜128 |
| うち Apple | 84〜90 |
| -60 / -70 / -80 dBm 以上 | 52〜72 / 72〜91 / 107〜113 |
| 1台あたりの受信パケット | 中央値 11 / 分。1回しか見えなかった端末は 1% |

- この場所では -80 dBm 以上が全端末とほぼ同数で、-80 の閾値は人数の変化を分けにくい可能性がある。校正では -60 と -70 も比べる
- 起動直後の約5秒しか観測していない窓は 75 台で、1回しか見えなかった端末が 44% あった。部分的な窓を校正から外す必要があることの裏付け

## 見つかった問題と対応

1. 起動直後の窓が、実際には数秒分しか観測していないのに 60 秒窓として送られていた。部分的な窓に `"partial": true` を付け、送信しないようにした
2. Android 15 以降の画面端までの描画で、画面上端の表示がステータスバーと重なっていた。システムバーの内側に表示するようにした
3. 開始から5分でスキャン結果が届かなくなった（下記）。3分ごとの再起動と、無受信30秒での再起動を入れた

### スキャン開始5分で結果が止まる

12:00:12 に開始したスキャンで、12:05 の窓のパケット数が前の分の約28%に落ち、12:06 以降は0になった。
Bluetooth プロセスのログに次の行があった。

```
12:05:12.730 W/BtScan.ScanManager: regularScanTimeout(Client(com.crowdlevel.node, ScannerId(2), mode[LOW_LATENCY, used=LOW_LATENCY])): Moving unfiltered scan to opportunistic scan
```

- 開始からちょうど5分。端末の DeviceConfig は `bluetooth/scan_timeout_millis=300000` だった（AOSP の既定は30分）
- 空の ScanFilter は「フィルタなし」と扱われた（`dumpsys bluetooth_manager` でも Filter 表示なし）
- 画面は点灯したまま、アプリは前面のまま、スキャン設定も LOW_LATENCY のままで、Bluetooth スタックの結果カウンタだけが止まっていた
- 12:04 と 12:05 の両方に現れた端末の受信回数は、メーカーを問わず一様に約28%に落ちていた。周囲の端末の変化ではなく、受信側の問題だった
- 設計時に想定した「30分降格」より短く、20分ごとの再起動では間に合わなかった。3分ごとに再起動するよう直した

## Ambient チャネルに残っている無効な点

- 11:41:59：Mac から curl で送った試験データ
- 11:56:00：上の問題 1 を直す前の部分的な窓（約5秒分）
- 12:05〜12:10：上の問題 3 で結果が止まっていた時間（12:05 は約28%、12:06 以降は0）
- 12:16〜14:47：毎分の送信は続いていたが、結果は0件。12:15 ごろに端末が USB から外れており（adb で見えなくなった）、画面が消えて OS がフィルタなしのスキャンを止めていた可能性が高い。端末を再接続して `dumpsys power` と `dumpsys bluetooth_manager` で確かめる

- 1時間以上の連続運転で、パケット数が落ちないこと
- 画面オフ時の挙動
